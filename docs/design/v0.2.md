# adaptive-iteration v0.2 設計草案

狀態:已定案(2026-09-25),實作中。

## 目標

1. **核心不耦合任何模型**:假設從哪裡來由使用者注入(`Proposer`),框架不知道 LLM 的存在。
   `openai` 相依整個移除,`core/` 只用標準函式庫。
2. **補上統計判定層**:框架根據每個單位的原始觀測值判定實驗結果,並附上不確定性。
   證據不足時不宣告 winner。判定規則可替換(`DecisionRule`)。
3. **帳本改存原始觀測值**:不再只存每組平均值,任何判定都能事後重算。

非目標:多臂(A/B/C…)實驗、多指標聯合判定、UI。v0.2 只處理單一主要指標的兩組比較。

## 為什麼要改(v0.1 的問題)

- `Ledger` 只存呼叫端傳進來的 `winner=True/False`,框架本身不判定任何東西。
- 實際使用端的判定規則是「每組只要幾個單位、平均差超過固定門檻就贏」,不看組內變異。
  每組只有幾個單位時,這種差距大多是雜訊。
- 帳本只存每組平均,事後無法重算。
- 缺資料沒有被排除:抓不到指標的單位被記成 0,因而被當成輸家。
- `HypothesisEngine` 寫死 OpenAI,呼叫端沒辦法控制模型參數(例如 reasoning effort)。
- 沒有去重:同一個想法換了幾個名字,就被當成幾個不同的實驗。

## 架構

```
使用者/adapter ──observations──▶ Ledger ──▶ Evaluator(DecisionRule) ──decision──▶ Ledger
                                   │
                                   └──▶ EvidenceSummary ──▶ HypothesisEngine(Proposer) ──▶ 去重後的 Experiment
```

兩個 Strategy 注入點,都用建構子注入(DI):

| 介面 | 誰實作 | 預設 |
|---|---|---|
| `DecisionRule` | 框架提供預設,使用者可換 | `WelchIntervalRule` |
| `Proposer` | 一律由使用者提供 | 無;LLM 版放在 `examples/` |

其他元件(`Ledger`、`Evaluator`、`EvidenceSummary` 建構)沒有替換的需求,維持具體類別。

介面一律用 `typing.Protocol`(結構型別),不用 ABC 繼承。任何有對應方法的物件都能傳入。

## 資料模型

### MetricSpec(每個實驗的主要指標定義)

```python
@dataclass(frozen=True)
class MetricSpec:
    name: str                      # "avg_view_pct"
    higher_is_better: bool = True
    min_effect: float              # 最小有意義差異(ROPE 半寬),例如 3.0 個百分點
    valid_range: tuple[float | None, float | None] = (None, None)  # 超出範圍的觀測值排除
```

`min_effect` 是整個判定的核心參數:它定義「差多少才算數」。沒有它就無法區分
「沒有差異」和「還不知道」。它必須由使用者依領域決定,框架不提供預設值。

### Observation(一個單位的一筆觀測)

```python
@dataclass(frozen=True)
class Observation:
    experiment_id: str
    variant: str                   # variant label
    unit_id: str                   # 例如 video_id
    metrics: dict[str, float | None]
    pair_id: str | None = None     # paired 模式下,同一組配對共用
    observed_at: str               # ISO-8601
```

`None` 代表「沒有資料」,永遠不會被當成 0。

### Decision

```python
class Outcome(Enum):
    A_BETTER = "a_better"
    B_BETTER = "b_better"
    EQUIVALENT = "equivalent"            # 差異確定小於 min_effect
    INSUFFICIENT = "insufficient"        # 還不知道,需要更多資料
    NO_DETECTABLE_DIFF = "no_detectable_diff"  # 已達樣本上限仍無法判定,結案

@dataclass(frozen=True)
class Decision:
    experiment_id: str
    outcome: Outcome
    metric: str
    effect: float | None           # mean(B) - mean(A),依 higher_is_better 調整正負號
    interval: tuple[float, float] | None
    confidence: float              # 0.95
    n_a: int
    n_b: int
    excluded: dict[str, int]       # 排除原因 → 筆數,例如 {"missing": 1, "out_of_range": 0}
    needed_n: int | None           # INSUFFICIENT 時,估計每組還需要幾個
    rule: str                      # 規則名稱
    rule_params: dict              # 判定當下的規則參數,供事後重現
    reason: str                    # 給人看的一句話
    decided_at: str
```

## DecisionRule

```python
class DecisionRule(Protocol):
    name: str
    def decide(self, a: Sample, b: Sample, spec: MetricSpec, paired: bool) -> Decision: ...
```

`Sample` 是已經過有效性檢查的觀測值(`Evaluator` 負責排除缺值、超出範圍的資料,並記錄排除數量)。

### 預設規則:`WelchIntervalRule`

判定時機由**時間窗**決定,不是逐筆:

- `window`(預設 7 天):實驗開始後每滿一個 window 才判定一次(第 1、2、3… 週),其餘時間一律回
  `INSUFFICIENT`。固定檢查點同時解決「偷看」問題。
- `maturity`(預設 72 小時):單位產出後要滿這段時間,指標才算穩定,才納入判定。
  例如週日上傳的影片,在第一週的檢查點還不算。
- `min_n`(預設 5):成熟樣本數的下限,是避免低產量領域一週只有 1、2 筆就判定的安全網,
  不是主要的判定依據。
- `max_windows`(預設 4):到了第 4 個檢查點仍無法判定,就結案為 `NO_DETECTABLE_DIFF`。

每個檢查點:

1. 任一組成熟樣本數 < `min_n` → `INSUFFICIENT`。
2. 計算 B−A 平均差的信賴區間:
   - interleaved:Welch t 區間(不假設兩組變異數相等)。
   - paired:配對差值的單樣本 t 區間。
   - 信賴水準依檢查點次數調整(Bonferroni:最多 4 次檢查,每次用 1−0.05/4 ≈ 98.75%),
     讓整個實驗的偽陽性率維持在 5% 以內。
3. 依區間與 ROPE `[-min_effect, +min_effect]` 的關係判定:
   - 區間下界 > 0 且點估計 ≥ `min_effect` → `B_BETTER`(預設 `superiority="significance"`)
   - 區間上界 < 0 且點估計 ≤ `-min_effect` → `A_BETTER`
   - 較嚴格的 `superiority="margin"`:整個區間要超過 `±min_effect` 才判勝
   - 整個區間落在 ROPE 內 → `EQUIVALENT`
   - 其他 → 若已是第 `max_windows` 個檢查點 → `NO_DETECTABLE_DIFF`,否則 `INSUFFICIENT`,
     並用目前的合併標準差估計 `needed_n`。

產量低的領域(例如每組每週只有 5 個單位左右)一週的量剛好碰到 `min_n` 下限,常常要跑到第 2 週
以後才判得出來;這種領域可以把時間窗拉長。

t 分佈分位數用標準函式庫實作(regularized incomplete beta + 數值反解),dev 測試對照 scipy。

**關於「不設停止條件」**:`max_windows` 只讓**單一實驗**結案,不影響整個迴圈。迴圈仍然無限持續產生下一輪
假設;沒有上限的話,一個效果極小的實驗會永遠卡住整條管線。

## EvidenceSummary(給 Proposer 的輸入)

純結構化資料,不含任何 prompt 文字:

```python
@dataclass(frozen=True)
class VariableEvidence:
    variable: str
    status: Literal["concluded", "equivalent", "open", "no_detectable_diff", "legacy_unverified"]
    best_variant: str | None
    effect: float | None
    interval: tuple[float, float] | None
    n_total: int
    experiments: list[str]         # experiment_ids

@dataclass(frozen=True)
class EvidenceSummary:
    domain: str
    metric: MetricSpec
    variables: list[VariableEvidence]
    open_experiments: list[str]
    metric_dispersion: dict[str, float]   # 各指標跨單位的標準差
    data_quality: dict[str, int]          # 累計排除筆數
```

另外提供 `EvidenceSummary.to_markdown()`,方便使用者自己的 LLM proposer 直接塞進 prompt。
這只是格式化工具,框架本身不使用它。

## 變數清單(VariableRegistry)

證據是依變數名稱累積的。同一件事換了名字,證據就會被拆散。所以框架維護一份變數清單,
proposer 可以用清單裡的變數,也可以提出新的,但新變數必須經過比對才能加入。

```python
@dataclass(frozen=True)
class VariableDef:
    name: str
    description: str
    aliases: tuple[str, ...] = ()
    execution: str | None = None   # 選填:管線如何實際執行這個變數(給人看,也給 proposer 參考)
```

- 清單存在帳本裡(`kind: "variable"` 以及 `kind: "variable_alias"`),帳本仍然是唯一的真相來源。
- `registry.merge(name, into=other)`:手動把重複的變數併在一起,舊名變成別名,證據合併計算。
  例如 `intro_visual_style` 和 `opening_visual_style` 這種語意相同、名字不同的變數,就用這個處理。
- 遷移 v0.1 帳本時,每個出現過的變數名稱都會自動登記一次。

## Proposer 與 HypothesisEngine

```python
@dataclass(frozen=True)
class Proposal:
    variable: str
    description: str
    variant_a: Variant
    variant_b: Variant
    tier: int = 2
    mode: Literal["interleaved", "paired"] = "interleaved"
    new_variable: VariableDef | None = None   # 提新變數時必填:定義與說明
    rationale: str = ""

class Proposer(Protocol):
    def propose(self, evidence: EvidenceSummary, n: int) -> list[Proposal]: ...

class DuplicateDetector(Protocol):
    def find_match(self, candidate: VariableDef, registry: VariableRegistry) -> str | None: ...

class HypothesisEngine:
    def __init__(self, ledger: Ledger, proposer: Proposer,
                 duplicates: DuplicateDetector = TokenSetDetector()): ...
    def generate(self, domain: str, spec: MetricSpec, n: int = 5) -> list[ReviewedProposal]: ...
    def accept(self, reviewed: ReviewedProposal) -> Experiment: ...
```

`generate` 的流程:

1. 建構 `EvidenceSummary`(包含整份變數清單),呼叫 `proposer.propose`。
2. 逐一審查每個 `Proposal`:
   - 用了清單裡的變數(或它的別名)→ 正規化成正式名稱。
   - 提了新變數 → 交給 `DuplicateDetector`。比對到既有變數就改用那個變數,並標記 `merged`;
     比對不到就標記 `new`。
   - 用了清單裡沒有、又沒附 `new_variable` 定義的名稱 → 丟棄,標記 `rejected: unregistered`。
   - 同一個變數已經有進行中的實驗 → 丟棄,標記 `rejected: already_open`。
   - 新變數沒有填 `execution` → 保留,但標記 `needs_execution`,提醒使用者確認管線做得到。
3. 回傳 `ReviewedProposal`(原始 proposal + 正規化後的變數 + 標記),不直接改清單。

`accept` 才會把新變數寫進清單,並產生 `Experiment`。沒被採用的提案不會汙染清單。

預設的 `TokenSetDetector` 把名稱和別名拆成 token 集合比對。例如 `visual_opening_style` 和
`opening_visual_style` 會判定為同一個。`intro_visual_style` 和 `opening_visual_style` 這種語意相近的,
字串規則抓不到,可以用 `registry.merge` 手動處理,或注入自己的 `DuplicateDetector`(包括用 LLM 判斷)。
框架不預設任何需要模型的實作。

## 重播(replay.py)

借用 Dream-RSI(arXiv 2609.14858)的想法:把記錄下來的歷史當成模擬器,用來評估「判定規則」本身,
新規則在重播上不比現行規則差才採用。

- `calibrate(pool, rule, spec, effect, per_window)`:從真實的逐單位數值池重抽樣,模擬實驗。
  `effect=0` 量偽陽性率,`effect>0` 量檢定力與判定所需週數。
- `gate(candidate, incumbent, ...)`:偽陽性 ≤ 5%,且各效果大小下的偵測率不低於現行規則,才建議採用。
- `replay(experiment, observations, spec, rule)`:依時間順序逐週重跑 Evaluator,每週只看得到當時已成熟的單位。

限制(與論文相同的保守原則):只重用實際觀測到的結果。能評估「怎麼判定、怎麼排程」,
不能預測沒測過的假設表現如何。

EvidenceSummary 另外提供 `cost`(已結案實驗每個明確勝負花了多少單位)與每個進行中變數的
`needed_n`,讓 proposer 可以偏好能快速判定的假設。

## 在真實資料上重播的結果(2026-09-25)

用一條實際在用的內容管線的逐單位資料(一個有雜訊、單位之間差異很大的指標)做校準,得到三個結論:

- **舊規則(每組幾個單位、平均差超過固定門檻就判勝)在沒有真實差異時,超過一半的機率會宣告勝負**,
  跟擲硬幣差不多。新的預設規則控制在 5% 以內。
- 兩種 B 勝門檻的偽陽性都在 5% 以內,但 `margin` 對真實效果的偵測率明顯低很多;
  `gate(significance, margin)` 建議採用 significance,因此定為預設。
- 能逐一重判的舊實驗很少:大多數每組只有幾個單位,而且缺資料嚴重。唯一資料量足夠的一個,
  重判結果是 `NO_DETECTABLE_DIFF`。

同一份資料也顯示,缺資料被記成 0 的情況確實存在,這正是「缺資料一律記 None」這條規則的由來。

## 0.3 追加(2026-09-25)

- `ProportionIntervalRule`:0/1 指標用 Newcombe 混合分數區間(由兩組 Wilson 區間組成),事件稀少時不會塌縮成一個點。
  對照 Newcombe (1998) 範例 (e) 驗證到小數第 4 位。
- 分層:`Observation.stratum`;`WelchIntervalRule(stratify=True)` 在各層內比較再依層大小加權合併,

  `ProportionIntervalRule` 暫不支援分層。
- `calibrate(..., pool_b=...)`:0/1 指標不能平移,改用第二個資料池模擬 B 組。

## 0.5 追加(2026-09-26)

- `PairedProportionRule`:成對的 0/1 資料(同一個項目在 A、B 下各評一次)。Newcombe (1998) 成對資料的 method 10:
  兩個邊際比例的 Wilson 區間,加上連續性校正的 phi 相關係數。依 `pair_id` 配對,缺配對的單位排除並回報。
  對照 Newcombe (1998) p.2641 第二列(n=50,20/12/2/16 → 0.0562 到 0.3292)驗證一致。
  模擬:虛無假設下偽陽性 0.6–2.8%(n=8–100);真實差 20 個百分點時,n=30 偵測率 51%、n=60 85%、n=100 98%。
- `ProportionIntervalRule` 遇到成對實驗時自動交給 `PairedProportionRule`,不再報錯。
- 套件根目錄匯出 `Sample`、`DecisionContext`、`RuleResult`,支援不經 Evaluator 直接判定一批離線資料。
- 需求來自 the-crucible(LLM 對話壓縮的離線實驗)。

## 0.6 追加:統計外包(2026-09-26)

  放棄零相依(安裝增加約 41 MB,含 numpy)。

  `tests/test_oracles.py` 對照 statsmodels(獨立比例 Newcombe、Welch、成對 t),誤差 1e-9 以內;
  沒有函式庫可比的,用模擬檢查 95% 區間的實際涵蓋率(成對 Newcombe 94.9–98.2%,分層估計約 95%)。

## 0.7 追加:自動迭代(2026-09-26)

- `Loop` 驅動器:專案提供 `collect`、`apply`、`proposer` 三個掛鉤,定期呼叫 `tick()`。
  每次:收集資料 → 判定 → 把結案的結論套用(贏的一方;沒有贏家就維持 A)→ 有空位就篩選並開始新實驗。
  `require_approval=True` 時,B 勝要人工 `approve()` 才套用。掛鉤出錯會記在報告裡,下次 tick 重試。tick 可以重複執行,結果不變。
- 分配(`assign`):同一層內哪一組比較少就分給哪一組,平手時用單位 ID 的雜湊決定,可重現。
  分配記在帳本;觀測資料的組別和分配不符時拒絕寫入。
- 事先篩選(`Screening`):proposer 附上 `expected_effect`,用帳本估計的標準差與每週產量,算出要幾個檢查點才看得出來。
  超過上限 → 拒絕;小於 min_effect → 拒絕;超過一半 → 標記 slow;資料不足 → 標記 unknown,不猜。
- proposer 打擊率:實驗記錄 `proposed_by` 與 `expected_effect`;證據摘要依 proposer 統計結果、成本、實際效果 ÷ 預估效果。
- 模擬(200 次、16 週、每週 60 單位、主題分佈偏斜):真實 +15 全部採用(中位數 1 週);無效果的改變誤採用 1.8%。
- 測試過程抓到兩個 bug:產量估計在歷史不滿 4 週時被低估(導致誤拒);同一時間重複 tick 會重複寫入未成熟的資料。

## 0.8 追加:放棄、重新開始、開始前核准(2026-09-26)

- 起因:實際使用端評估改用 Loop 前提出的需求。
- `abandon`:實驗結束但沒有結論。不再判定、不再收資料、不會被套用;釋出變數與名額;證據裡顯示為 abandoned;打擊率另外計算。必須寫原因。
- `restart`:放棄舊的,用同樣定義重建新實驗(`restart_of` 指回舊的),從新的時間點開始,採用那時生效的判定設定。分配不沿用。
- `Loop(require_start_approval=True)`:通過審查的提案加入帳本但不開始,佔名額;`approve_start` 開始,`reject_start` 等同放棄。
- 影子模式:複製帳本檔 + 什麼都不做的 apply + 回傳空清單的 proposer(不需要新功能,已加測試與說明)。
- 修正:`config_for` 改為從帳本讀實驗的最新狀態。之前如果傳入建立時、尚未開始的 Experiment 物件,會被當成未開始而套用最新設定,等於繞過「不能中途放寬標準」。
